# 标准流题目契约与统一用例池

Status: ready-for-agent

## What to build

把题目与判题输入模型直接改造成标准输入 / 标准输出语义。题目本体只保留语言无关内容，示例用例与隐藏用例归入一套统一用例池并明确公开/隐藏标记和稳定顺序。新的 controller、service 和后台管理契约直接以标准流题目为主语义，不再保留旧函数式字段作为兼容层。

## Acceptance criteria

- [ ] 题目本体只描述题意、输入说明、输出说明、约束、示例和判题方式，不再承载共享函数签名或共享代码骨架
- [ ] 示例用例和隐藏用例统一建模为一套标准流用例池，显式区分公开/隐藏，并保证所有公开用例稳定排在隐藏用例之前
- [ ] 用户端题目详情、后台题目详情和核心 service 契约统一使用标准流题目语义，不再继续扩散 `sharedFunctionName`、`sharedCodeSkeleton`、`sharedTestCases` 之类旧主字段
- [ ] 试运行与正式提交入口都从统一用例池读取标准流用例，而不是继续读取旧的函数参数对象测试数据

## Blocked by

## Agent Brief

**Category:** enhancement
**Summary:** Replace the existing function-call question contract with a stdin/stdout question contract and a single ordered standard-stream case pool.

**Current behavior:**
The program-question domain still treats shared function metadata and shared parameterized test cases as the primary contract. Question entities, service results, controller responses, admin create/update requests, workflow outputs, and run/submit entrypoints all still revolve around fields such as `sharedFunctionName`, `sharedCodeSkeleton`, `sharedTestCases`, language-level `functionName`, and function-style `testInputs`. Public examples and official judging data are not modeled as one explicit standard-stream case pool with stable ordering and public/hidden markers.

**Desired behavior:**
The primary question contract should become standard input / standard output. The question body should carry only language-agnostic statement content and judging semantics. Public examples and hidden judging cases should be represented as one unified standard-stream case collection with explicit visibility and stable order, where all public cases precede all hidden cases. Core backend contracts, question-detail APIs, admin question-management contracts, and the data consumed by run/submit flows should all speak in terms of standard-stream questions and standard-stream cases rather than function signatures, code skeletons, parameter objects, or legacy shared test-case fields.

**Key interfaces:**
- The core question aggregate and its persistence model — it should expose language-agnostic statement content plus standard-stream judging data, not shared function-call metadata.
- The question detail service/result/response contract used by the user-facing problem detail flow — it should return standard-stream question semantics and a unified case representation rather than `sharedFunctionName`, `sharedCodeSkeleton`, and `sharedTestCases`.
- The admin question create/update contract — it should accept standard-stream question content, unified case-pool data, and per-language assets without requiring shared function signatures or shared code skeleton fields.
- The language-asset contract for supported languages — it should remain language-specific, but represent runnable starter code / reference assets rather than function-call entry metadata as the primary question contract.
- The run/submit command/request boundary — it should resolve public or full standard-stream cases from the unified case pool instead of consuming function-style `testInputs` sourced from legacy shared test-case JSON.
- The workflow question-generation output contract — it should target standard-stream question data and the unified case pool so later issues can consume the new contract directly.

**Acceptance criteria:**
- [ ] The primary backend question contract no longer requires or exposes shared function-call fields as the canonical question shape.
- [ ] Public examples and hidden judging data are modeled as one unified standard-stream case pool with explicit public/hidden markers and stable order.
- [ ] The unified case pool enforces the ordering rule that all public cases come before all hidden cases.
- [ ] User-facing question detail responses, admin question-management contracts, and core service-layer question results all use the standard-stream contract instead of expanding legacy shared function-call fields further.
- [ ] Run and submit entrypoints resolve their case data from the unified standard-stream case pool rather than legacy parameter-object test-case structures.
- [ ] Existing tests around question contracts are updated to validate the new standard-stream semantics and unified case-pool behavior.

**Out of scope:**
- Replacing the execution backend with go-judge or removing GraalVM execution internals.
- Implementing asynchronous official submission orchestration, verdict persistence, or frozen judge-package execution.
- Introducing immutable question-version publication, session-version binding, SPJ packaging, or publish-gate automation.
